The CRM lives where the conversations already are

More than a thousand real sales leads, handled inside the messenger the team already had open all day. The design question was not what the CRM should do. It was where it should be, so that using it costs nobody an extra tab.

Scale1,100+ live leads
Built withNode, SQLite, embedded UI
RoleProduct model, implementation, operations
Sits insideThe team's existing messenger

Why placement is the design

Every CRM has the same failure mode, and it is never technical. The salesperson has the conversation somewhere — a phone call, a chat window — and is then expected to go somewhere else and describe what happened. That second step is unpaid administrative work performed after the interesting part is over, and it is the first thing dropped on a busy day.

Once it is dropped, the CRM starts to lie. And a CRM that is out of date is worse than no CRM, because decisions get made from it. Reports are produced. The pipeline shows deals that closed in March.

So this one is not a destination. It is built into the messenger the team already keeps open: the lead is a thread, the history is the thread, and recording an interaction is what happens automatically when you have the interaction. There is no second step to skip.

Intake

Leads arrive from a contact form on a public site, which means an endpoint on the open internet accepting writes from anyone. Three things happen to a submission before it is allowed to become a lead.

The assignment step is the one that earns its place. A lead that arrives without an owner belongs to everybody, and a thing that belongs to everybody is attended to by nobody until it is too old to be worth attending to. Assigning on arrival means that at any moment, for any lead, there is exactly one person who would be surprised to learn it had been ignored.

Scoring matters for the same unglamorous reason. In a list of a thousand conversations, a new enquiry sorted by arrival time appears below several hundred older ones. It is not that a low score means a bad lead — it means an invisible one.

Operating a system with real customers in it

This is the project where the data is other people's business. That changes how it is worked on, more than any architectural choice does.

  • Deployment is by patch, never by reset. The usual convenience of forcing the server to match the repository is unavailable here, because work has been done on the server that exists nowhere else. A hard reset would be a silent data loss dressed up as a deployment.
  • The database is backed up nightly, on a schedule that assumes nobody is watching. The interesting question about a backup is never whether it ran; it is whether anyone has ever restored it. An unrestored backup is a belief, not a control.
  • Cache-busting is mandatory, not optional. Users keep this interface open for days. Shipping a fix without changing the asset version means shipping it to nobody, while the log says the deployment succeeded.
The general principle

Software adoption is a question about attention, not features

Every argument in this write-up reduces to the same thing. The tool is used because using it does not require remembering to. The lead is assigned because an unowned item is an unattended item. The score exists because being at the bottom of a long list is the same as not existing.

None of that is a technical achievement, and all of it is the difference between a CRM with a thousand live leads and a CRM with a thousand rows nobody trusts. The hard part of an internal tool is almost never the tool.
