A building written as geometry, not imported as a model

A hundred and fifteen paintings drawn from a public collection and hung across ten halls of a building that exists only as code. The engineering question underneath: what has to be true for a room on the internet to be somewhere you can cite?

Livemuseum.eprisjournal.com
Collection115 works, 10 halls
Built withthree.js, Python build step, static hosting
RoleCuration, architecture, implementation

The premise

Most virtual museums are galleries with a camera. You move, images pass, nothing is anywhere in particular. The moment you want to say “the third wall of the second hall”, you find there is no such place — only a coordinate in a scene that will change next time the layout is adjusted.

This one is built the other way round. A hall is an address. It has a URL, a fixed wall length, a date span and a list of works, and that list is written in a file which has nothing to do with the geometry. The building can be rebuilt entirely without a single citation breaking, because the citation points at the hall, not at a position in a model.

The building itself is written as geometry in code rather than imported as a prepared 3D model. That is a deliberate trade: a model file would look richer, and it would be an opaque binary that nobody can diff, review or adjust without the tool that made it. Concrete described in a hundred lines of arithmetic can be changed by reading it.

Getting the pictures

The works come from a major public collection that exposes both a search API and IIIF, the standard for serving images of cultural objects at arbitrary sizes. Two rules govern the intake, and both are about rights and obligations rather than code.

Only public-domain works are taken. This is checked per object against the collection’s own rights field, not assumed from age — a photograph of an old painting can carry its own claim, and the field is the only authority worth trusting.

And the collection requires requests to identify themselves with a specific header. Omit it and the image endpoint refuses, in a way that looks exactly like a network failure. This is a fair demand: a public institution serving very large images for free is entitled to know who is asking. Anyone building against a cultural API should expect a condition like it and read the terms before the code.

The hang is curated, not sorted. Halls carry an argument — a period, a way of handling light, a shared problem — and the order within a hall is chosen. Sorting by date would have been one line of code and would have produced a database listing with walls.

The failure that shaped the front end

A browser can take back a hardware drawing surface at any moment: too many tabs, another application demanding the GPU, a laptop deciding to save power. Every serious three-dimensional page must survive this. Without handling, the canvas simply goes blank — no error, no message, a grey rectangle where a room was.

Here it was worse than a blank hall. The museum persists across transitions between halls, so a single lost surface followed the visitor everywhere. One hall failed; from then on, every hall was empty. The museum appeared to be entirely broken, and only for the people it had happened to.

What it cost to learn

The state that outlives the page is the state that hurts

The bug was hard to find because it was not reproducible in the hall where it appeared. Everything about that hall was fine. The damage had been done in a different hall, minutes earlier, and had travelled through the thing designed to make navigation feel smooth: a persistent surface that survives route changes.

Every long-lived object bought for performance — a shared canvas, a cached connection, a module-level singleton — is also a channel along which one failure reaches parts of the system that never touched it. It is worth writing down, for each such object, what happens when it dies. Usually nobody has, and the answer turns out to be everything downstream, silently, until reload.

How it ships

The whole museum is generated as static files by a single build step and copied to a server. There is no application running behind it. For an archive this is the correct default: nothing to keep patched, nothing to fall over at three in the morning, and a copy of the entire institution can be handed to someone as a folder.

Exhibitions are curated through a small admin that sits alongside, and the generator now lives on the server rather than on a laptop. That sounds like a detail and is not: a generator that only exists on one machine means the museum can only be rebuilt by one person, which is a preservation problem dressed as a convenience problem.
