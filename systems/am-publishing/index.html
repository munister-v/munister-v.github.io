Keep the catalogue independent of who is selling the book

A publisher's site where each title carries a set of offers rather than a link to one shop. Distribution deals change; the writing about the book should not have to be edited when they do.

One modelling decision

The natural way to build a publisher's catalogue is to give each book a buy button pointing at whichever retailer the publisher currently uses. It works immediately and it is wrong in a way that only shows up later, when the deal changes and a hundred pages need editing — or worse, when the book is available in one region and not another, and the single link is right for some readers and useless for the rest.

So a title carries a set of offers: which shop, which region, on what terms. The page selects among them. Nothing about the book's description depends on commercial arrangements, which means those arrangements can change without anybody touching editorial text.

The fallback matters as much as the matching. A reader in a region with no offer is not shown a dead end; they are sent to the publisher's own channel. A catalogue whose answer to can I buy this? is sometimes nothing has failed at the only job the page has.

Separate services, deliberately

The public site is static. Transactional checkout and the radio station run as their own services elsewhere. This is more moving parts than one application, and it buys something specific: the failure of any one of them is survivable.

  • The catalogue survives everything. It is files. If payment integration breaks, or the radio process dies, the books are still readable and the site is still up.
  • The radio has its own life. Streaming audio has entirely different uptime and resource characteristics from a catalogue page, and coupling them means the catalogue inherits the streaming service's problems for no benefit.
  • Integrations are off by default. Shipping and analytics connections are declared in configuration and disabled until deliberately switched on. A half-configured integration that is live is worse than one that does not exist, because it fails in ways that look like the site is broken.
What it cost to learn

The client edits the same branch you do

The publisher edits book entries directly in the repository's main branch. That is intentional — they are the authority on their own catalogue and should not need a developer to correct a subtitle.

It also means the branch moves under your feet between the moment you start work and the moment you push, so every push begins by fetching and replaying on top of theirs. Forgetting once means either a merge nobody asked for or, if resolved carelessly, quietly reverting their afternoon.

The wider point is about who is on the other end. A collaborator who does not use version control cannot be expected to resolve a conflict, and will not know one has happened. The obligation to check sits entirely with the person who does — which makes fetch-before-push a courtesy, not a technicality.

A note on rendering prose

One small thing worth recording because it recurs in every editorial system. The editors separate paragraphs by pressing return once. The site was rendering submitted text with whitespace preserved and no paragraph structure at all — visually almost right, structurally a single undifferentiated block, with no paragraph elements for a screen reader or a search engine to work with.

The fix understands both conventions: one return or two, both produce real paragraphs. It is worth doing properly because the alternative is asking non-technical writers to format text a particular way, which is a request they will reasonably ignore.
