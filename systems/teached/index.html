A lesson is a structure, not a document

Fifty-one tools for language teachers, all reading the same thing. The bet: if a lesson is stored as structure rather than as a printed page, it can be revised, shared and re-run — and one afternoon's preparation stops being disposable.

Scope51 tools, 30+ classroom games
RoleProduct model, architecture, releases
DeploysContinuously, from main

The bet

A teacher prepares a worksheet on Sunday evening. On Monday it is a PDF. By Friday it is a PDF with pen on it, and next term it is prepared again from nothing, because a document cannot be adjusted for a different class without being rebuilt.

The alternative is to store what the teacher actually decided — these words, this task, this constraint, this expected answer — and treat the worksheet as one rendering of that. Then the same material becomes a board activity, a game, or a printed page, and changing the class means changing the structure rather than retyping the artefact.

That is the whole product thesis, and it is the reason there are fifty-one tools rather than fifty-one products. They are views.

Generated pages have to be measured

A generated worksheet has to fit a sheet of paper. The obvious approach is to estimate: so many characters, so many lines, so much height. This is wrong every single time, because text wraps — and where it wraps depends on the font, the container, the language and the exact words. An estimate is a guess about typesetting made without doing any typesetting.

So the worksheet is rendered first and measured afterwards. Not estimated, measured: lay it out, ask the browser what the box actually became, and reflow if it overran.

There is a trap inside the measuring, too. The obvious property for “how tall is this content” reports the height of the scrollable area, which is never smaller than the visible box — so content that comfortably fits reports the box size rather than its own, and the fit loop concludes it is exactly full. Measuring means measuring the right thing, and the right thing is rarely the first property with a promising name.

What it cost to learn

One modern colour function broke every export

Export to image works by walking the live page and repainting it onto a canvas. The library that does this parses colour values itself, and it predates the colour-mixing functions the redesign had adopted. A single computed color-mix() anywhere in the captured subtree threw — and the whole export failed, not the one element.

The instinct is to hunt down and rewrite the offending styles. That is a losing game: the value leaks in through at least five routes, including inherited properties and rules nobody remembers writing, and it comes back the next time someone uses a modern colour. The fix was to intercept style resolution during capture and hand the library a colour it understands, leaving the page itself alone.

When a third-party consumer of the DOM cannot cope with something valid, adapt at the boundary. Editing the whole codebase to suit one library’s parser is a debt that compounds, and it silently forbids a feature of the platform for everyone who works on it later.

Saving what actually changed

The board keeps its state by hashing what is on it, and only writing when the hash moves. This is a standard and sensible way to avoid saving constantly.

It also had a hole worth describing, because the shape recurs. The hash was computed over the set of cards and their positions — which detects adding a card and moving a card, and does not detect editing the text inside one. A teacher could rewrite a sticky note, see no error, and lose the change. The system was working exactly as written; what was written did not include the most common edit.

Any change-detection scheme is a claim about what counts as a change, and that claim is usually made implicitly by whoever wrote the hash. It is worth stating out loud, because the omissions are invisible from the inside — everything looks correct, and the missing case simply never fires.

Where the difficulty actually lives

Very little of the hard work in this system is algorithmic. It is in the places where a clean model meets an uncooperative medium.

  • A card with a fixed height and text that wraps. This has been repaired four separate times. Height set by constant will meet a longer word, in every language, forever; the layout has to be told to follow its contents rather than be told a number.
  • Elements that clip their own affordances. A card that hides overflow also hides the resize handle sitting just outside it, and swallows the clicks aimed at it. The visual rule and the interaction rule were the same rule, and nobody thought of it that way until the handle stopped working.
  • A phone is not a narrow desktop. The mobile layout was assembled from four independent sources of rules that each had an opinion about the same login window. The result was not a bug in any of them.
  • Service workers cache confidently. Replacing an icon without advancing the version ships the old icon to everyone who has ever visited, and it looks like the replacement failed.
