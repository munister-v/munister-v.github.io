Horreum
Retail operations core · Method, model, invariants

The shop is a view. The operation is the system.

Horreum is the back office behind a clothing retailer: roughly 2,800 products, some 7,100 size-level variants, and a catalogue that arrives as spreadsheets from people who have never agreed on a column name. The client is not named here, and neither is the deployment. What is worth writing down is the part a customer never sees, and the four decisions the rest of it rests on.

The problem

Retail runs on documents. A workbook from the supplier, a price list, a photograph of a shelf, a message on Friday saying the last two went this morning. Every one of them is true when it is written and slightly wrong an hour later, and not one of them can be asked a question.

The storefront was the visible half of this job and by some distance the smaller one. A shop can be rebuilt in a season. The operation behind it has to answer the same dull questions every working day: how many of this article are left in 42, what did we pay for it, which supplier was cheaper last spring, what has not moved since March. None of those are design questions. They are questions about whether the business wrote anything down in a form that can be read back.

So Horreum moves the source of truth rather than redecorating it. Not a spreadsheet mailed on Mondays, and not a content system in which a product is a document and a size is a word inside it. One relational model: a product, its variants, the movements that changed them, the receipts that paid for them. Everything else, the storefront included, is a view of that model rather than a copy of it. A copy is a thing that drifts.

Method

Under the retail vocabulary sit three problems that have names of their own, and naming them is what makes the design arguable instead of a matter of taste.

Schema matching. An unknown tabular layout has to be mapped onto a fixed target schema. The awkward part is the asymmetry: the evidence for the mapping lives in a header and a handful of sample values, while the cost of getting it wrong is paid once per row, silently, across the whole file. That asymmetry is the argument for deciding the mapping once per layout and for showing the decision to a person before it is used.

Deterministic record linkage. Each offer row has to be attached to the variant it describes, using identifiers of different scope: one issued per size, one per article by the manufacturer, one per article by us. The linkage is deliberately deterministic rather than probabilistic. A scored guess is a reasonable instrument when the cost of a near miss is small; here a near miss puts a supplier’s quantities on somebody else’s garment, which is not a slightly worse match but a wrong number on a shelf.

A materialised aggregate under concurrent writers. The per-product total is a cached fold over its variants, and every cache of that kind fails the same way: two writers, one stale read, a total that nobody can reproduce. It is kept correct not by careful application code but by structure, which is the general move this whole system is built on. Uniqueness is a constraint in the database, atomicity is a transaction, and the aggregate is recomputed from the rows that own the truth.

Everything the system knows arrives as an electronic document: a supplier workbook, a goods receipt, an order, a payment callback. The document is kept as received and the derived record is kept separately, because a document is evidence and a record is an interpretation of it, and the two stop agreeing at different speeds. Reconciliation is then possible at all, which is the practical reason to pay for the duplication.

Stated that way, the import is an algorithm rather than a sequence of screens, and each step can carry its cost. Below, n is rows in the file and k is sizes of one article. The number of model calls is a function of layouts, not of n, and that is the single most important line in the table.

Algorithm 1one workbook to committed stock
  1. Detect the layoutO(h) over the header

    Both header rows are read and normalised, then matched against the signatures of layouts already known. One decision per file, taken before a single data row is touched.

  2. Map the columnsO(1) model calls per layout

    A known signature maps by rule. An unknown one costs exactly one model call, whose input is the header and whose output is a column map that a person reads on screen before it is applied. Never O(n), which is what makes the step affordable and reviewable at the same time.

  3. Resolve each row≤4 indexed lookups per row

    The identity ladder is walked in fixed order and stops at the first hit: per-size code, barcode, our article, the manufacturer’s article. Deterministic, so the same file resolves the same way twice, which is what makes a re-run safe.

  4. Group the residueone pass, O(n)

    Rows that resolved to nothing are grouped by the manufacturer’s article, so an article in k sizes becomes one product carrying k variants rather than k products. The descriptive columns of the group are carried into the new product instead of being dropped with the row.

  5. Report the differencepure, writes nothing

    The dry run is a function of the file and the current state that returns counts of created, updated and held. It has no side effects, so it can be run as often as anybody wants to look at it.

  6. Commitone transaction

    Products, variants and movements are written together. Either the file landed or it did not; there is no third state in which half a supplier’s prices are live.

The invariants below are the part worth arguing about, because each one names the mechanism that holds it. An invariant maintained by discipline is a habit, and habits are not preserved by deployments.

Invariantswhat holds, and what holds it
I1The product total equals the sum of its active variants after every committed movement.Held by recomputation inside the same transaction as the movement, and checkable by rebuilding the total from the journal and comparing.
I2Every change of a quantity leaves exactly one journal row, carrying its cause.Held by a single write path. Sale, import and hand correction call one function; nothing else may write a quantity.
I3No value used for matching is ever generated by us.Held by omission: the barcode generator is never run against real variants, and the size code is computed on read rather than stored.
I4Every reported valuation carries the step that produced it.Held by the resolver returning provenance with the number, so a receipt-based cost and a rule-derived one cannot be confused downstream.
I5An ambiguous row is held. It is never completed with a default.Held by the absence of a fallback in the parser. There is no default price to fall back to, so no code path can quietly invent one.

Each of those five is carried by a table, and each table names who is allowed to write it. That is the whole model on one screen: open it table by table, and every field there carries the reason it exists rather than only its type. The three that decide the rest are linkable on their own: the variant, which holds the only quantity anybody counted; the movement, which is the account of why it changed; and the product, which carries a total it is not allowed to type.

Intake

Goods arrive as files, and the files do not agree with one another. Five shapes so far: an export from the old content system; a master workbook in a legacy single-byte encoding where a size repeated three times means three units on the shelf; an eight-column price list where one row is one offer; a fifty-five-column export whose header is two rows deep, one row of human labels and one of machine codes; and whatever the next supplier invents.

The instinct is a parser per supplier. That fails quietly, which is the worst way to fail. A reordered column produces plausible numbers rather than an error, and nobody finds out until a size is sold that does not exist.

Detection therefore reads the header, not the rows. A recognised export goes to rule-based mapping. Only a genuinely unfamiliar file is handed to a model, and it is asked to map columns once per layout, never rows. That distinction is the entire reason a model is allowed anywhere near this pipeline: four thousand rows would be four thousand chances to invent a price, while one header is a single decision, cheap, repeatable and small enough for a person to read on screen before anything is written. Files mapped that way are badged as machine-read in the panel, because that is something the operator should be told rather than something discovered later.

The branch worth defending is the red one. A row that cannot be resolved is held, not guessed. A pipeline that invents a price for an ambiguous row will eventually sell something for the wrong money, and nobody will be able to say which row did it. Holding a row costs somebody five minutes. Guessing one costs a reconciliation that was never budgeted for.

The unit of meaning is not the row

The step that took the most rewriting is the dull one in the corner. Rows matching nothing in the catalogue used to become new products one at a time, so an article in seven sizes landed as seven near-identical products. An earlier version was worse: it read the descriptive columns, name and brand and colour and composition and country and gender, into the preview grid and then stored none of them, so an unmatched row lost everything except its numbers.

Both are the same mistake in different clothes, which is treating the row as the unit of meaning. A row is an offer. The unit of meaning is the article, and the repair was to group unmatched rows by it before creating anything. On the fifty-five-column export that is 4,097 rows becoming 1,622 products, with nothing left unmatched.

Identity

Three identifiers that look like one, and a fourth that must never be stored at all.

Collapsing them into a single tidy field called SKU is the obvious move and the wrong one. Matching a supplier price list needs the manufacturer’s article. A customer holding the garment reads the code on the tag, which is ours. The barcode belongs to whoever printed it. They answer different questions, so they stay different columns, and an imported row walks them in a fixed order until one of them matches.

resolution orderhow one imported row finds its variant
offer_codefirstthe supplier’s own per-size code, when the file carries one. The most specific thing in the row
barcodesecondEAN. Empty on all ≈7,100 variants in this catalogue, which is a fact about the catalogue rather than a gap to be filled in
articlethirdour internal code: the one printed on the tag, and the one a customer quotes back on the phone
factory_articlefourththe manufacturer’s article, present on nearly every product. Identifies the article, never a single size
size codecomputedinternal code plus size, assembled for display and for search, never written to a column

There is a barcode generator in the codebase, and it is deliberately not run against real variants. Generated codes would sit in precisely the field the next supplier file matches on, and the file after that would attach its quantities to values we invented ourselves. An import that matches on a number of our own making is not an import. It is a coin toss that issues a receipt.

The empty barcode column has a matching piece of restraint in the schema. Its index is partial, defined only over rows where the code is not empty, so today it indexes nothing and costs nothing to keep, and on the day a supplier finally sends real codes it is already there. An index over a column that is empty everywhere is not a small waste, it is a promise to maintain something nobody uses; a partial index is the same promise made only for the rows that will exist.

The size code is the same argument one step further. It is derived from two columns that already exist, so writing it down would create a third place where the truth is kept and a first opportunity for the three to disagree. It is therefore assembled on the way out, for the page and for the search index alike.

The retailer’s own rule was blunt and correct: every code a product has must appear on its page, and search must find the product by any of them. Search covers name, brand, internal code, factory article, barcode, offer code, the computed size code and the numeric id. Two of its behaviours look like bugs and are not. A query that exactly equals the code of exactly one product jumps straight to that product; the condition is one exact match, not one result, because substring matching drags in other people’s codes and a redirect on “one result” would confidently land on the wrong garment. And codes are never upper-cased in CSS, because thirty-four articles contain lower-case letters, and a code shown in a case it does not have is a code the customer cannot check against the tag in their hand.

The legacy names carry the article in brackets on the tail, in 2,642 of them. It is stripped for display at read time and left alone in the database, because search matches on the name column, and cleaning it would break finding a product by the code that used to live there.

Stock

Stock is held per cell: a matrix of product against size, with the movement that produced each number kept beside it. This is the decision the rest of the system rests on, and it is what makes the questions at the top of this page answerable by a query rather than by a phone call.

A sale, an applied import and a hand correction are three different stories about the same number, and each of them is somebody’s alibi. Routing all three through one function is not tidiness. It is the only way the journal can be believed: if any path can write a quantity without leaving a movement behind, the journal becomes a partial record, and a partial record of stock is worse than none, because it looks complete.

The total on the product row is a mirror, derived and never typed. Keeping it at all is a compromise made on purpose: a catalogue page showing sixty products would otherwise ask for a sum over variants sixty times to decide which cards say “in stock”. A cache is acceptable when it has one writer and a way to be rebuilt from scratch. This one has both.

stockthe cell, and the reason it changed
variant.sizetextthe column of the matrix. Seeded from the product’s attributes at zero the first time the matrix is opened, so an untouched size exists rather than being absent
variant.stock_qtyintegerthe cell. The only quantity in the system that anybody actually counted
variant.activebooleana size that is not stocked at all, kept distinct from a size that is stocked and currently at zero
movement.typetextimport, receipt, sale, return, adjust, writeoff. The column that turns a number into an account of itself
movement.deltaintegerthe change that was asked for, signed
movement.qty_afterintegerthe quantity that actually resulted. Kept beside the delta on purpose: the two disagree exactly when something was clamped, and that disagreement is the evidence
product.stock_qtyintegerthe mirror: sum of the active variants, recomputed inside the same transaction as the movement, never edited by a person
product.is_in_stockbooleanderived alongside it, so a listing page can filter on a column instead of on a subquery

Concurrency

Everything above is written as though one thing happens at a time. It does not. A supplier file lands while a customer is at the checkout, and both of them want the same row. This is where a stock system is actually decided, because the failure here is not a crash but a number that is quietly wrong and reproducible by nobody.

There are two write paths, and they are different on purpose. A sale knows the change but not the result: one unit less, whatever is there. An import knows the result but not the change: the supplier says twelve, and what the difference turns out to be is our problem, not theirs. That asymmetry decides how each is written.

The sale is one statement. The read, the arithmetic and the write cannot be pulled apart by another transaction, because there is nothing between them to interleave with, and the resulting quantity comes back from the same statement to be journaled.

The import cannot use that form, because it needs the previous value in order to know what to record: the movement is written with the difference, and a difference needs a before. So it takes the row explicitly, SELECT … FOR UPDATE, computes the target, writes it, and journals the change it turned out to be. The lock is held for the length of the transaction, which is the entire point: anybody else who touches that row in the meantime waits, rather than reading a value that is about to stop being true.

Both paths clamp at zero, and that is a deliberate choice with a cost attached. Stock is a count of things on a shelf, and a negative count is not a fact about a shelf, so the floor stays. But a clamp destroys information: two units sold against one unit in stock and one unit sold against one unit in stock leave the same row behind. That is why the journal keeps both numbers, the change that was asked for and the quantity that resulted. When they disagree, the sale was clamped, and the row where they disagree is findable with one query rather than remembered as a story by whoever noticed.

The mirror is recomputed at the end of the same transaction, over the active variants only, and it carries a boolean beside it so that a listing page filters on a column instead of running a subquery per card.

One honest gap, since a write-up that only lists the parts that came out well is an advertisement. An order applies its lines in the order the cart happens to hold them, not in key order. Two orders that share two variants can therefore take the same two locks in opposite orders and deadlock; the database detects it and rolls one of them back, so nothing is corrupted, but somebody sees a failed checkout that had no business failing. Sorting the lines by variant id before applying them removes the possibility entirely. It is a two-line change, it is not in yet, and writing it down here is cheaper than rediscovering it from a support message.

Snapshot or delta

A supplier file has a meaning that is not written anywhere in the file, and getting it wrong is the most expensive mistake in this whole system. Some files are a delta: here is what changed. Others are a snapshot: here is everything I have. The two look identical, rows of articles and quantities, and they say opposite things about what is not in them.

In a delta, absence means nothing at all. In a snapshot, absence is the loudest statement in the document: an article that is missing from a full stock list is not unchanged, it is gone. Treating a snapshot as a delta leaves phantom stock on the shelf and sells things nobody has. Treating a delta as a snapshot empties the catalogue.

So the mode is a property of the source, set once per supplier channel and not inferred per file. When the mode is snapshot, the import does one more pass after the rows it recognised: every variant that belongs to that source and did not appear in the file is set to zero, and each zeroing writes its own movement, typed as an import, carrying a note that says it was absent from a full snapshot. The catalogue is allowed to lose stock, in other words, but never silently: absence becomes an entry rather than a gap.

Reversal

An import that can be undone is worth more than an import that is always right, because the second kind does not exist. Every run records itself item by item: the variant, the quantity before, the quantity after, and why the row was touched. That table is what a rollback reads.

The interesting part is what a rollback refuses to do. Time has passed since the run: sales have happened, somebody has corrected a size by hand, a second file may have landed. Restoring the old quantities blindly would erase every one of those, quietly, in the name of undoing something else. So the rollback first compares what it wrote with what is there now, row by row, and if anything has moved since, it stops and says how many rows have.

When the check passes, the restore is still written forwards. Old quantities are put back with their own movements, typed as adjustments and attributed to the rollback, and the original import movements stay exactly where they were. Nothing is deleted, because the journal is an account of what happened and an undo is one of the things that happened. The run is marked as rolled back and keeps its own row.

That is the general shape of undo in any system with more than one writer: not a time machine, but an operation that states what it expects to find, refuses when it does not find it, and leaves its own trace when it succeeds. The version that just restores the old values is one line shorter and will eventually delete somebody’s afternoon.

What it cost

Not one of the five file shapes contains a purchase price. Suppliers send what they would like you to sell at, not what you paid, and the recommended retail price in the workbook is the one number in it that is nobody’s fact.

Cost is therefore resolved rather than stored, in a fixed order, and every figure the system reports carries the step that produced it: a weighted average from posted receipts, failing that a figure entered by hand, failing that a value derived by rule from the selling price. Provenance travels with the number because it changes what the number is allowed to decide. A valuation whose provenance is unknown is not a fact, and it will be used in a decision anyway. That is the problem.

On top of the journal sit the two reports the business acts on. Turnover and dead stock: what has moved, how fast, and what has not been touched since a date the operator picks. Purchase-price history: what different suppliers charged for the same article over time, and how far apart they were. The second is empty until receipts are posted, and it says so plainly instead of averaging what little it has. An average built from two receipts and an assumption looks exactly like an average built from two hundred, and the reader cannot tell which one they are holding.

Finding one thing

Search here is not a feature, it is how the system is used. Somebody in the shop reads a code off a tag, somebody on the phone repeats half a name, somebody in the office pastes a supplier’s article out of an email. One query language over eight fields, two shapes of query, and one lesson that arrived at production speed.

What it cost to learn

Two statements, one array of parameters

Listing runs two queries over one array of bound values: the rows, with ordering and limit and offset, and the count, with only the filter. The count took a prefix of that array, computed as its length minus the two parameters belonging to limit and offset. It was correct for months on a coincidence: the ranking parameter also appeared inside the filter, so the arithmetic came out even.

Switching off fuzzy trigram matching for code-shaped queries removed that duplicate, and every search by code began returning a server error: bind message supplies 13 parameters, but prepared statement requires 12. The boundary is now recorded as a value the moment the filter is finished, and sort parameters are bound after it. The rule that outlived the bug: when two statements share one array, the boundary between them is a fact to be written down, not arithmetic on the end of it.

The second half of it is about testing. The deploy check asked for the home page, which exercises neither branch. Queries here come in two species, word-shaped and code-shaped, and a change to the filter routinely breaks exactly one of them. Both are now in the smoke test by example, not by category.

Operating it

The parts that have cost the most time appear in neither diagram, because they are not features.

  • Media became an index, not a directory listing. Roughly 13,700 image files were being read off the disk on every request that needed to know what existed. They are indexed in the database now and hashed by content, which as a side effect surfaced 527 groups of byte-identical duplicates that nobody had been able to see before.
  • The lockout counted a header the client writes. Repeated failed logins were counted per client address taken from a forwarded header, which anyone can set to anything. Rate limiting moved to the layer that knows who is actually connected, with the panel and the login endpoint limited separately.
  • A full import still truncates. Rebuilding the catalogue from a file removes the hand corrections made in the panel since the last one. Until a merge import exists, imports are staged deliberately rather than run casually, and the limitation is written on the screen that runs them rather than in somebody’s memory.
  • A backup is verified by restoring it. Checking that a dump decompresses proves the file is not corrupt and nothing else. The recovery drill ends in a restore into a scratch database, because that is the only test that answers the question being asked of it.
What it nearly cost

An unreferenced file is a claim, not an observation

Part of the media work was a reclaim report: files that nothing in the database points at can be deleted. It listed 394 free files, and among them all 63 brand logos, every one of which was on the live site at that moment. They are referenced as /uploads/brands/name.png?v=2, and comparing paths as exact strings matched none of them.

Nothing was deleted, because the list was read before it was acted on, and a category that suspiciously equalled the entire set of brand logos was the tell. Reference matching is normalisation, not equality: strip the query string, and look in every place a path can be written, which here meant the product image documents, the legacy image column, the brand logos and the content store. The same pass also learned that 58 apparently orphaned files were the untrimmed originals of those logos, kept on purpose. A reclaim job reports a hypothesis, and it has to be built so the hypothesis is cheap to check and expensive to act on, rather than the other way round.

Where it stands

Live, and used every working day. The catalogue is imported rather than typed, stock is answerable at size level, cost carries its own provenance, and the storefront reads from the same model instead of keeping a version of the truth of its own.

Some of the work was deletion. Feed generators for two marketplaces were removed when the business stopped selling through them, along with the plan that depended on them. A generator nobody reads is not free: it still has to stay correct through every schema change, and it quietly makes every later decision heavier.

Next: a merge import that keeps hand corrections, receipts posted so the price history has something to average, and intake by message so that a supplier file becomes a preview without anyone opening the panel at all. The test of a back office is not what it displays. It is whether a question about last spring can be answered without asking anybody to remember.
