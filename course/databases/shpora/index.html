Розділ 1

СУБД і типи моделей даних

OA 1-1 – 1-4 · ЛК1–2

БД — структурований набір пов'язаних даних; СУБД керує зберіганням, цілісністю та паралельним доступом. На відміну від файлової системи, БД не дублює дані під кожну програму окремо і тримає обмеження цілісності в одному місці. Відправна точка проєктування — бізнес-вимоги, словесний опис потреб замовника.

Об'єктнамодельдані як об'єкти з методами

Розділ 2

Зв'язки й ERD-нотація

OA 2-5, 2-6 · ЛК5

Кожен зв'язок описується з двох боків: кардинальність (один / багато) і обов'язковість (мусить / може) — нотація «ворона лапка» (Crow's Foot).

Пастка на іспиті

Обов'язковість читається з боку зв'язку, не з боку сутності

Символ біля Факультету описує, чи обов'язковий цей зв'язок для Студента — а не навпаки. Питання завжди одне: «чи може екземпляр цієї сутності існувати без цього зв'язку?» Якщо ні — засічка (обов'язково); якщо так — коло (необов'язково).

Розділ 3

Нормалізація 1НФ – 3НФ

OA 3.3 · ЛК8

Мета — усунути аномалії вставки / оновлення / видалення і дублювання даних. Курс зупиняється на 3НФ.

Нормальні формипослідовно
1НФформаатомарні значення; немає повторюваних груп в одній комірці
2НФформа1НФ + немає часткової залежності від частини складеного PK

Пастка на іспиті

2НФ стосується лише складеного PK

Якщо первинний ключ таблиці — одна колонка, вимога 2НФ виконується автоматично: часткова залежність можлива тільки від частини складеного ключа. Питання «чи в 2НФ?» для таблиці з простим PK — пастка, відповідь завжди «так».

DDL і обмеження цілісності

CREATE TABLE student (
  student_id   NUMBER        PRIMARY KEY,
  email        VARCHAR2(60)  UNIQUE NOT NULL,
  faculty_id   NUMBER        REFERENCES faculty(id) ON DELETE CASCADE,
  gpa          NUMBER(3,2)   DEFAULT 0 CHECK (gpa >= 0)
);
-- складений первинний ключ (проміжна таблиця M:M)
CREATE TABLE enrollment (
  student_id NUMBER, course_id NUMBER,
  CONSTRAINT pk_enrollment PRIMARY KEY (student_id, course_id)
);
ALTER TABLE student ADD phone VARCHAR2(20);
ALTER TABLE student MODIFY phone VARCHAR2(30);
ALTER TABLE student DROP COLUMN phone;
ALTER TABLE student RENAME COLUMN gpa TO avg_score;
RENAME student TO students;
TRUNCATE TABLE students;                 -- очистити всі рядки, без відкату
DROP TABLE students CASCADE CONSTRAINTS;
Обмеження цілісності7 видів
PRIMARY KEYPKунікальний, не NULL, ідентифікує рядок; може бути складеним
REFERENCESFKпосилання на PK іншої таблиці
ON DELETE CASCADEFKвидалення батьківського рядка видаляє й дочірні
ON DELETE SET NULLFKвидалення батьківського рядка обнуляє FK у дочірніх
UNIQUEUKунікальність без ролі ідентифікатора

Пастка на іспиті

DROP TABLE без CASCADE CONSTRAINTS падає з помилкою

Якщо на таблицю посилається чужий FK, звичайний DROP TABLE завершиться ORA-02449. CASCADE CONSTRAINTS прибирає лише самі обмеження в інших таблицях — сусідні таблиці й дані в них залишаються на місці.

Розділ 8

ORDER BY і JOIN

OA 6.8–6.9 · ЛК16–17 
SELECT s.name, f.title
FROM student s
JOIN faculty f ON s.faculty_id = f.id
ORDER BY s.gpa DESC;
Пастка на іспиті

LEFT JOIN підставляє NULL, а не 0 чи порожній рядок

Для факультету без жодного студента COUNT(s.student_id) поверне 0 (функція ігнорує NULL), а s.name у тому ж рядку буде саме NULL, не порожнім текстом. Порівняння WHERE s.name = '' такий рядок не знайде — потрібен IS NULL.

Підзапити

Додатково · поза програмою курсу

Запит усередині запиту — у WHERE, FROM або SELECT. Виконується перед зовнішнім, якщо не корельований.

-- однорядковий: = > < допустимі
SELECT name FROM student
WHERE gpa > (SELECT AVG(gpa) FROM student);

-- багаторядковий: потрібні IN / ANY / ALL
SELECT name FROM student
WHERE faculty_id IN (SELECT id FROM faculty WHERE city = 'Київ');

-- корельований: посилається на зовнішній запит, рахується для кожного рядка
SELECT s.name FROM student s
WHERE EXISTS (SELECT 1 FROM enrollment e WHERE e.student_id = s.student_id);
Типи підзапитів4 типи
однорядковийпідзапитповертає одне значення; працює з = < > <= >=
багаторядковийпідзапитповертає список; потрібні IN, ANY, ALL
корельованийпідзапитвикористовує стовпець зовнішнього запиту, рахується на кожен рядок
EXISTS / NOT EXISTSпідзапитперевіряє лише наявність рядків, не їхні значення
Пастка на іспиті

NOT IN мовчки ламається на NULL

Якщо підзапит у NOT IN (...) поверне хоча б один NULL, весь зовнішній запит не поверне жодного рядка — без помилки, просто порожній результат. Безпечніший варіант у такому випадку — NOT EXISTS, він на NULL так не реагує.

Вступ до PL/SQL

Додатково · поза програмою курсу

Процедурне розширення SQL в Oracle: змінні, умови, цикли навколо звичайних SQL-команд. Анонімний блок — найпростіша одиниця виконання.

DECLARE
  v_gpa   student.gpa%TYPE;
  v_name  VARCHAR2(60) := 'Іванов';
BEGIN
  SELECT gpa INTO v_gpa FROM student WHERE name = v_name;
  IF v_gpa >= 4.5 THEN
    DBMS_OUTPUT.PUT_LINE('Відмінник: ' || v_name);
  END IF;
EXCEPTION
  WHEN NO_DATA_FOUND THEN DBMS_OUTPUT.PUT_LINE('Не знайдено');
END;
Структура блоку3 частини
DECLAREнеобов'язковооголошення змінних, курсорів, констант
BEGIN ... ENDобов'язкововиконувані оператори: SQL, IF, LOOP, присвоєння
EXCEPTIONнеобов'язковообробка помилок часу виконання (наприклад, NO_DATA_FOUND)
%TYPEоголошеннятип змінної береться зі стовпця таблиці — не розходиться при зміні схеми

Oracle APEX: середовище розробки

Додатково · інструмент курсу (ЛР1, ЛР9, ЛР10, ЛР14)

Oracle APEX (Application Express) — хмарна low-code платформа: пишеш SQL/PL-SQL у браузері, а веб-застосунок поверх бази збирається з готових компонентів, без окремого фронтенд-стеку. Курс використовує APEX і як середовище виконання SQL (замість встановлення власної БД), і як конструктор невеликого застосунку в фінальних лабораторних.

Oracle

Oracle SQL Developer Data Modeler

Додатково · інструмент курсу (ЛР3–8)

Настільний інструмент для ER-моделювання: логічна модель малюється мишею, а фізична схема й готовий DDL-скрипт генеруються з неї автоматично — саме тому в курсі ERD, нормалізація і DDL йдуть послідовно через один інструмент.

Рівні моделі в інструменті3 подання
Logical Modelподаннясутності, атрибути, зв'язки, UID — те саме ERD з нотацією Barker (ворона лапка)
Relational Modelподаннятаблиці, стовпці, PK/FK — результат команди Engineer
Physical Modelподаннясхема під конкретну СУБД (Oracle, тип і версія) з точними типами даних
Робочий процес4 кроки
Engineer to Relational Modelкомандаперетворює Logical Model у Relational Model за правилами з розділу 4 (1:M → FK, M:M → таблиця)
Attribute Mappingкрокузгодження атрибута логічної моделі зі стовпцем і типом даних фізичної (розділ 5)
DDL GenerationкомандаPhysical Model → готовий .sql-файл із CREATE TABLE та обмеженнями

Огляд

Бази знань та експертні системи

Оглядовий розділ · ЛК18–19

Експертна система — ПЗ, що імітує рішення експерта у вузькій галузі: база знань (факти + правила «якщо…, то…»), механізм виведення, інтерфейс користувача.

БД проти бази знаньпорівняння
База даних→факти; запит повертає готові дані
База знань→факти + правила; запит може дати новий висновок

Підсумок

На іспиті

Чотири речі, які найчастіше забувають

1. Спочатку модель словами: сутність → атрибути → зв'язок → кардинальність, і лише потім SQL.

2. 1:M — FK на стороні «багато»; M:M — завжди окрема таблиця; забутий цей крок ламає весь DDL.

3. HAVING — тільки після GROUP BY і тільки з агрегатними функціями; WHERE агрегати не бачить.

4. Підзапит із IN вимагає списку значень (багаторядковий), а з = — рівно одного (однорядковий); переплутати — отримати ORA-01427.
