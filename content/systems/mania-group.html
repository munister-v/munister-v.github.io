The problem

The shop that existed worked, in the sense that it served pages and took orders. What it could not do was answer questions. How many of this jacket are left in 46? is not a question a page can answer, because in WordPress a product is a document and a size is a word inside it. Stock lived in the supplier’s head and in a spreadsheet emailed on Mondays.

Everything downstream inherited that. A price change meant editing pages. A new supplier meant retyping a workbook. Reporting meant counting by hand. None of these are bugs; they are the consequences of one modelling decision made years earlier, and no amount of plugin work reverses it.

So the rebuild is not a redesign. The visible shop is the smallest part of it. The work is to say what a product is, what a variant is, what an order is and what payment is — and then to keep those four answers stable while everything else changes around them.

Intake

Goods arrive as spreadsheets. Not one format: a WooCommerce export from the legacy system, and workbooks from suppliers who each invented their own column names, in two languages, sometimes with the header on row four.

The first instinct is to write a parser per supplier. That scales badly and fails silently — a new column order produces plausible nonsense rather than an error. The pipeline instead tries a rule-based parser first, and only when the file is genuinely unrecognised does it ask a model to map columns onto the schema. The model runs once per layout, not once per row: it is being asked to read a header, which is a job it does well and cheaply, rather than to transform data, which it does expensively and unreliably.

The branch that matters most is the red one. A row that cannot be resolved is held, not guessed. This is the whole difference between an import that can be trusted and one that cannot: a pipeline which silently invents a price for an ambiguous row will, sooner or later, sell something for the wrong money, and nobody will know which row did it. Holding a row costs someone five minutes. Guessing costs a reconciliation.

What a product turned out to be

Three identifiers that looked like one. The seller’s own internal code, the manufacturer’s factory article, and a barcode — which, in this catalogue, is empty on every single variant. Collapsing them into a single “SKU” field would have been tidy and wrong: matching a supplier’s price list against our catalogue needs the factory article, while a customer’s question about “the code on the tag” needs ours.

Stock is held at variant level, as a matrix of product against size. That is the modelling decision the whole system rests on. It is also the one that makes the question at the top of this page answerable at all.

The order

An order has two states, and they are not the same state. Whether the parcel has shipped and whether the money has arrived are independent facts, and a shop that stores them in one column starts lying the moment either happens without the other.

Cash on delivery is shipped but unpaid for a week. An online prepayment is paid but unshipped until Monday. There is no ordering of these that a single status column can express, and every attempt to force one produces a status list like paid_but_not_shipped that grows a new member every time reality does something new.

Checkout re-checks the size before it writes anything. The stock a customer saw was read when the page rendered, and between then and the submit button someone else may have bought the last one. Re-checking at the moment of writing is the difference between an oversold order and a polite refusal.

Money

Payment providers retry. This is not a failure mode to be defended against grudgingly; it is the documented, correct behaviour of every provider worth using, because the alternative — a callback lost to a network blip and an order never marked paid — is worse. The provider assumes the receiver is idempotent, and if the receiver is not, the provider’s correct behaviour becomes the receiver’s double-payment.

Idempotency here is not application logic that checks whether it has seen this callback before — that check is a race, and under retries a race is exactly what you get. It is a unique index on the pair of provider and provider reference, with the write expressed as an upsert onto it. The database decides. Two simultaneous deliveries of the same callback cannot both insert, because the index will not let them.

The raw callback body is stored alongside, untouched. When a payment is disputed months later, the useful artefact is what the provider actually sent, not our parsed summary of it. Never keep only your own account of someone else’s money.

What it cost to learn

A forwarded header is user input

The admin panel locks an account after repeated failed logins, keyed by client address. The address came from a forwarded header, which any client can set to anything. The lockout was therefore trivially bypassed by varying it — and worse, could be aimed at someone else by sending their address with bad passwords.

The fix was not more application code. Rate limiting moved to the layer that actually knows who is connecting, with the panel and the login endpoint limited separately, and repeat offenders dropped at the firewall. The general lesson has outlived the bug: anything a client can write is not identity, no matter how conventional the header name.

Operating it

The parts of this system that have cost the most time are not in any of the diagrams above, because they are not features.

  • The build outgrew the machine. A production build on a small VPS competes with the running site for memory and loses. The deploy stops the process manager, builds under an explicit heap cap, then starts again — slower, and it finishes.
  • A synchronisation flag deleted the catalogue images. Mirroring a local directory to the server with deletion enabled removed everything the server had that the laptop did not, which was all the product photography. Deploy scripts now carry their exclusions themselves, rather than depending on whoever runs them remembering.
  • The server is sometimes ahead of the laptop. Work done directly on the server is real work. Treating the local copy as the source of truth and pushing over the top erases it silently. Every deployment now begins by asking what the difference actually is.
  • A verified backup is one that has been restored. Checking that a dump decompresses proves the file is not corrupt and nothing else. The recovery procedure here ends in an actual restore into a scratch database, because that is the only test that answers the question being asked.

Where it stands

The shop is live and selling. The catalogue is imported rather than typed, stock is answerable at size level, and orders carry a history that can be read back. The direction of travel is from shop toward back office: the same data model now serves an operations panel where stock, price imports and orders are handled in one place, rather than split between a storefront and a spreadsheet.

The measure of the rebuild is not the interface. It is that questions the old system could not answer are now answered by a query.
